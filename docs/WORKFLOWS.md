# 任務、驗收與長計畫工作流程

## 選最小相關範圍

```text
node tools/context.cjs --list
node tools/context.cjs bungee
node tools/context.cjs pendulum
node tools/context.cjs --task chart
node tools/context.cjs --task legacy-stairs
```

路由工具只輸出檔案位置、動態行號及檢查指令，不會自動讀入所有來源或執行測試。它是上下文選擇工具，不是權限、審批或自動完成系統。

- 題目問題：先找 ID 的模型區塊及 kind 場景分支，再擴大到共用邏輯。
- 畫面問題：先找 HTML 結構和 CSS；不要一開始讀所有物理公式。
- 圖表問題：用 chart 路由；確認圖表是 viewport 的下方兄弟區塊，不能以覆蓋或 z-index 隱藏問題。
- 舊版獨立頁面：不要套用共用引擎的修改後就以為獨立頁也修好了。
- 測試失敗：先看實際失敗斷言與對應模型／控制；不要先重寫整份驗證器。

## 新增一個題目

1. 用 new-experiment 路由，確認同類場景是否可共用。
2. 寫出物理假設、狀態、參數、單位、終止條件及可驗證的參考結果。
3. 註冊模型、場景，必要時補取景／額外讀值；保留共用圖表與播放行為。
4. 新增物理驗證，不只驗證函式能執行。總覽及下拉選單會自動列入模型。
5. 有獨立入口例外時，同步更新 `assets/library.js` 及 `docs/routes.json` 的 entryOverrides；不要只改文件。
6. 更新 README 的索引、CURRICULUM 的範圍；重新執行後才更新 QA 的數量及證據。
7. 執行對應檢查、必要的視覺預覽及路由驗證。若新增場景未可視或模型有錯，不能只以總覽存在宣告完成。

## 一般修正的交付

- 用一句話說明變更後的行為，完成可逆且已授權的修改，不把例行工作轉成多餘確認。
- 修改範圍保持集中，保留使用者尚未提交的其他變更。
- 檢查目標問題與相鄰共用功能；通過後不無理由重複執行同一批檢查。
- 完成訊息區分實際測試、離線 Canvas 預覽和真實瀏覽器觀察。沒有工具能力時不能暗示已做過。
- 本機檔案分享優先使用存在且無查詢字串的入口。必要時新增小型入口頁連到共用實驗，而不是複製整套 UI。

## 長計畫與交接

長期目標、跨多個實驗的批次改動或可能跨上下文的工作，使用一份獨立計畫：

1. 由 `docs/plans/TEMPLATE.md` 複製為 `docs/plans/YYYY-MM-DD-short-name.md`。
2. 在 INDEX 登記狀態及連結。只讀與目前任務相關的活動計畫，不掃描所有歷史文件。
3. 先保留完整原始目標與驗收條件，再分成可交付里程碑；不要以子集取代原目標。
4. 工作區狀態是事實來源：續作時查 `git status --short`、相關檔案及真實執行 handle。前次「已完成」文字只能用來找證據。
5. 在有實質進展、發現問題、驗證完成、停等外部輸入或交接時更新計畫，保持短小可用。不要把每一次命令原樣貼成流水帳。
6. 保留下一個具體動作、檔案與符號，以及仍需的驗證；留下足以直接繼續工作的資訊。
7. 完成時逐項核對完整驗收條件，標記證據與未驗證限制，再將 INDEX 狀態改為完成。暫停須來自使用者明確指示，真正阻塞要記錄原因；不要因工作很長就宣稱被阻塞。

## 文件同步原則

- 持續規則改 AGENTS；模型契約改 PHYSICS；任務路由改 routes.json；執行中狀態改對應計畫。
- 不把同一份規格複製到每個文件，也不把臨時狀態寫成永久規則。
- 檔名／符號／kind／入口或驗證依賴變動後，跑 `node tools/check-context.cjs`。
- `QA.md` 的歷史通過數量可能過期；以本次程式和實際檢查輸出更新，不硬改數字湊齊。
